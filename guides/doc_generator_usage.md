# Doc Generator 使用指南

> 本指南介绍如何使用 `doc-generator` SKILL 从真实交付场景出发生成高质量工程文档。

---

## 1. 概述

### 解决什么问题

在工程交付过程中，团队经常需要编写技术方案、评审规则、最佳实践等文档。传统方式面临两难：

- **纯人工编写**：耗时长、易遗漏、依赖个人经验
- **纯 AI 生成**：内容抽象、缺乏人感、无法保证正确性、可能包含幻觉

`doc-generator` SKILL 通过 **"AI 辅助整理 + 真实案例驱动 + 人工校对保证"** 三步模式解决这一问题：

| 维度 | 纯人工 | 纯 AI | doc-generator |
|------|--------|-------|---------------|
| 效率 | 低 | 高 | 中高（AI 辅助 + 人工校对） |
| 正确性 | 依赖个人水平 | 无法保证 | 人工校对后可验证 |
| 实战价值 | 取决于经验 | 偏理论 | 基于真实交付案例 |
| 可追溯性 | 一般 | 无来源 | 每条观点标注来源 |

### 适用场景

- 编写技术评审规则
- 整理最佳实践文档
- 沉淀踩坑经验与反模式
- 生成面向特定角色的交付指南

### 不适用场景

- 纯理论性学术文档（无真实项目支撑）
- 产品营销文案
- 代码注释或 API 文档（使用其他专用 SKILL）

## 2. 快速开始

### 3 步生成文档

**第 1 步**：确认真实素材来源

确保 `knowledge/real-world/` 目录下有相关案例文件。如果没有，请先贡献真实案例（参考[第 5 节](#5-如何贡献真实案例)）。

**第 2 步**：调用 doc-generator SKILL

向 AI 发出指令，指定目标主题和素材来源：

```
使用 doc-generator SKILL，基于以下真实素材生成一份文档：
- 主题：[文档主题]
- 素材来源：knowledge/real-world/[案例文件.md]
- 输出位置：[目标路径]
```

**第 3 步**：校对并更新可信度

AI 生成初稿后（默认 `⏳ 待验证`），人工校对内容，确认无误后更新头部标注为 `✅ 已验证`。

---

## 3. 完整工作流

### 步骤 1：收集真实素材

从以下位置收集素材：

| 素材类型 | 位置 | 说明 |
|---------|------|------|
| 交付案例 | `knowledge/real-world/` | 真实项目交付记录 |
| 踩坑经验 | 各案例中的"踩坑经验"章节 | 实际问题与教训 |
| 最佳实践 | 各案例中的"最佳实践"章节 | 可复用的方法论 |
| 已有知识 | `knowledge/` 各子目录 | 已验证的知识库文档 |

**操作要点**：
- 按主题归类素材（技术方案/踩坑经验/最佳实践/复盘总结）
- 标注每个素材的来源路径（确保可追溯）
- 如果暂无真实案例，标注 `⚠️ AI生成`，声明"暂无实战验证，仅供参考"

### 步骤 2：生成初稿（AI 辅助）

AI 辅助整理文档结构，但**内容必须引用真实来源**。

初稿要求：
- 每个核心观点附带 `[来源: <路径或项目名称>]` 标注
- 初稿默认为 `⏳ 待验证` 级别
- 包含"踩坑经验"章节（不可省略）
- 避免 AI 编造的示例代码

文档头部标注格式：

```markdown
> **可信度**: ⏳ 待验证
> **说明**: AI 根据真实交付案例整理初稿，等待人工校对
> **最后更新**: YYYY-MM-DD
```

### 步骤 3：标注待验证项

明确标记哪些内容需要人工校对，使用 `<!-- TODO-VERIFY: <说明> -->` 标记。

常见待验证项：
- 技术细节的准确性
- 数据/指标的真实性
- 结论的合理性
- 规则的完整性

建议使用表格跟踪：

```markdown
| 待验证项 | 验证方法 | 责任人 | 状态 |
|---------|---------|--------|------|
| [描述] | [如何验证] | [谁负责] | ⏳ |
```

### 步骤 4：人工校对

作者或领域专家确认内容正确性：

1. 逐条核对技术细节与真实项目的一致性
2. 确认每条观点都有真实来源支撑
3. 修正不精确或超出证据范围的描述
4. 补充缺失的踩坑经验或最佳实践
5. 处理所有 `<!-- TODO-VERIFY -->` 标记

### 步骤 5：更新可信度

校对通过后，将可信度从 `⏳ 待验证` 升级为 `✅ 已验证`：

```markdown
> **可信度**: ✅ 已验证
> **说明**: 基于 [N] 个真实交付案例，经 [角色] 校对确认
> **最后更新**: YYYY-MM-DD
```

### 步骤 6：发布

- `✅ 已验证` 文档：可发布到知识库，作为权威参考
- `⏳ 待验证` 文档：仅限团队内部流转评审
- `⚠️ AI生成` 文档：**禁止发布到知识库**

---

## 4. 可信度评级说明

### 三级可信度评级

| 级别 | 标识 | 含义 | 可发布 |
|------|------|------|--------|
| ✅ 已验证 | `Verified` | 人工阅读过原文/原始资料，内容经过校对 | 是 |
| ⏳ 待验证 | `Pending` | AI 辅助整理初稿，等待人工校对 | 仅限内部评审 |
| ⚠️ AI生成 | `AI-Generated` | 纯 AI 生成，未经验证，仅供参考 | 否 |

### 升级规则

**⚠️ → ⏳**（需满足全部条件）：
- 添加了真实案例引用或来源链接
- 标注了具体哪些部分需要验证
- 制定了人工校对计划（含预计完成时间）

**⏳ → ✅**（需满足全部条件）：
- 作者/领域专家确认内容正确性
- 已完成全部待验证项的校对
- 更新了"说明"字段为已验证状态的描述

### 维护要求

- 已验证文档内容过期超过 **6 个月**，需降级为 `⏳ 待验证`
- 发现已验证文档存在错误时，立即降级为 `⏳` 并标注错误项
- 所有可信度变更应在"最后更新"日期中体现

完整规范请参考：[内容可信度评级规范](../knowledge/governance/content_quality_rules.md)

## 5. 如何贡献真实案例

真实案例是 doc-generator 的基石。贡献流程：

### 步骤

1. 复制模板文件：`knowledge/real-world/template.md`
2. 填写所有必填字段：

| 字段 | 必填 | 说明 |
|------|------|------|
| 可信度 | ✅ | 文档可信度等级 |
| 项目 | ✅ | 脱敏后的项目描述 |
| 交付时间 | ✅ | YYYY-MM 格式 |
| 作者 | ✅ | 文档作者 |
| 背景 | ✅ | 真实项目背景 |
| 交付过程 | ✅ | 实际交付步骤 |
| 踩坑经验 | ✅ | 至少一条实际问题记录 |
| 最佳实践 | 可选 | 可复用的方法论 |
| 反模式 | 可选 | 应避免的做法 |
| 可复用产出 | 可选 | 脚本/模板/检查清单等 |

3. **脱敏检查**：确保不含客户名称、敏感数据、内部架构细节
4. 提交到 `knowledge/real-world/` 目录

### 脱敏规则

| 需脱敏 | 处理方式 |
|--------|---------|
| 客户名称 | 使用行业 + 规模描述（如"某电商平台"） |
| 具体金额 | 使用量级描述（如"百万级"） |
| 内部架构细节 | 保留技术方案，隐去内部组件名称 |
| 个人身份信息 | 使用角色描述（如"安全专家 A"） |

### 贡献案例的价值

- 为后续文档生成提供真实素材
- 帮助团队避免重复踩坑
- 沉淀可复用的交付方法论
- 提升整体交付质量

## 6. 常见问题

### Q1: 如果没有真实案例怎么办？

可以生成 `⚠️ AI生成` 级别的文档，但必须：
- 在头部明确标注 `⚠️ AI生成`
- 声明"暂无实战验证，仅供参考"
- **禁止发布到知识库**
- 尽快补充真实案例以升级为 `⏳` 或 `✅`

### Q2: 人工校对需要多久？

通常 **30 分钟 ~ 2 小时**，取决于：
- 文档复杂度
- 待验证项数量
- 专家排期情况

AI 辅助整理阶段仅需约 30 分钟，人工校对是主要时间投入。

### Q3: 可以跳过人工校对直接发布吗？

**不可以**。`doc-generator` SKILL 的核心原则是"人工校对保证"，未经验证的文档：
- `⏳ 待验证`：仅限内部评审
- `⚠️ AI生成`：禁止发布到知识库

### Q4: 如何处理跨领域主题？

如果主题涉及多个领域且无对口专家：
1. 标注 `⚠️ AI生成`
2. 附带"建议寻找领域专家确认"提示
3. 主动联系相关领域专家进行校对

### Q5: 可信度降级后怎么处理？

当已验证文档出现以下情况时需降级：
- 内容过期超过 6 个月
- 发现事实性错误
- 依赖的上游规则/标准发生变化

降级操作：更新头部可信度标注，在"说明"中注明降级原因。

### Q6: doc-generator 与其他 SKILL 的关系？

| SKILL | 关系 |
|-------|------|
| `book-knowledge-ingestor` | 互补：前者从书籍提取知识，后者从交付案例生成文档 |
| `reviewer-simulator` | 配合：生成的文档可通过 reviewer-simulator 模拟评审 |
| `submission-builder` | 配合：文档可作为交付包的组成部分 |

### Q7: 文档需要遵循特定的格式吗？

是的，参考 [文档结构模板](../skills/doc-generator/SKILL.md#文档结构模板)，核心要素包括：
- 头部可信度标注（必填）
- 背景与场景
- 核心观点（附来源标注）
- 踩坑经验（必填，不可省略）
- 可落地实践
- 待验证项（如有）
