# BOS-FS 产品交付辅助 Skill 适用场景

> **可信度**: ⏳ 待验证
> **说明**: 基于AI辅助生成初稿，内容结构参考行业标准，建议结合实际项目经验使用
> **最后更新**: 2026-06-01

> **定位**: BOS-FS 是**产品交付辅助 Skill**，可集成到任意 AI Agent（Cursor / Trae / OpenHands / Claude Code），帮助**任何交付团队**把项目的"能力"转化为"可被理解、评估、接受的交付物"。
>
> 用途: 明确 BOS-FS 在实际交付项目中的应用场景，帮助团队负责人/项目经理/工程师判断是否值得引入。
>
> 受众: 产品团队负责人、项目经理、技术负责人、安全工程师、任何需要交付标准化文档的角色。

---

BOS-FS 适用于**所有需要把项目能力转化为可被理解、评估、接受的交付物的场景**。安全交付是其中一个重要的子集。

| # | 场景类别 | 适用角色 | 核心痛点 | 效率提升 |

| 3 | [开源项目交付](#场景-3-开源项目交付) | 开源维护者 | 开源项目缺乏标准化交付物 | 显著 |

## 场景 1: 软件产品交付

### 背景

产品团队完成开发后，需要将技术能力转化为面向客户/管理层的交付文档。技术团队擅长实现，但往往不擅长将技术能力转化为商业价值表达。

### BOS-FS 如何帮助

| 阶段 | 传统方式 | BOS-FS 方式 |
|------|---------|------------|
| 需求理解 | 口头交接或零散文档 | Goal Refiner 提炼 persona/problem/solution/outcome |
| 价值表达 | 技术语言描述功能 | Outcome Mapper 转换为 Feature→Capability→Outcome |
| 文档生成 | 手动编写 README/说明书 | README Refactor 自动生成标准化文档 |
| 质量预审 | 交付后才发现问题 | Reviewer Simulator 模拟五类评审，提前发现问题 |
| 交付构建 | 零散文件打包 | Submission Builder 生成完整交付包 |

### 输入输出

**输入**: 项目描述、功能列表、目标用户信息、技术架构描述

**输出**:
- 产品价值说明 (面向管理层/客户)
- 技术文档 (面向开发/运维团队)
- 用户指南 (面向终端用户)
- 完整交付文档包 (README/CONTRIBUTING/SECURITY/CHANGELOG)

### 效率指标

| 指标 | 传统方式 | BOS-FS |
|------|---------|--------|
| 文档准备时间 | 2-3 天 | 4-6 小时 |
| 技术→商业语言转换 | 手动，易遗漏关键价值点 | 自动映射，确保完整性 |
| 评审通过率 | ~50% | ~85% |

## 场景 2: 技术文档交付

### 背景

技术文档（API 文档、架构设计文档、部署指南等）需要满足特定质量标准，但编写者往往难以自查文档是否完整、准确、易于理解。

### BOS-FS 如何帮助

| 阶段 | 传统方式 | BOS-FS 方式 |
|------|---------|------------|
| 文档规划 | 凭经验确定章节 | 基于知识体系的标准化模板 |
| 内容编写 | 手动编写，格式不统一 | 结构化引导，自动格式化 |
| 质量检查 | 人工评审，易遗漏 | 自动审查完整性/准确性/可读性 |
| 评审模拟 | 交付后才收到反馈 | 模拟技术评审/架构评审视角 |

### 输入输出

**输入**: 项目代码、架构描述、API 定义、部署配置

**输出**:
- 架构设计文档
- API 参考文档
- 部署与运维指南
- 完整技术文档包

### 效率指标

| 指标 | 传统方式 | BOS-FS |
|------|---------|--------|
| 文档编写时间 | 3-5 天 | 1-2 天 |
| 质量审查轮次 | 2-3 轮 | 0-1 轮 |
| 文档一致性 | 依赖个人水平 | 标准化模板保证 |

## 场景 3: 开源项目交付

### 背景

开源项目需要完整的交付物（README、贡献指南、行为准则、许可证、安全策略等），但很多项目缺乏这些标准化文件，导致社区参与度低。

### BOS-FS 如何帮助

| 阶段 | 传统方式 | BOS-FS 方式 |
|------|---------|------------|
| 许可证选择 | 随意选择或忽略 | 基于项目特点推荐 |
| 贡献指南 | 简单几句话 | 标准化贡献流程文档 |
| 安全策略 | 往往缺失 | 自动对齐 OWASP 基准 |
| 信任声明 | 无 | 对标 CII Best Practices 自动生成 |

### 输入输出

**输入**: 项目描述、技术栈、依赖列表

**输出**:
- README (项目介绍/安装/使用/贡献)
- CONTRIBUTING.md (贡献指南)
- CODE_OF_CONDUCT.md (行为准则)
- SECURITY.md (安全策略)
- LICENSE (许可证建议)
- 信任声明 (对标行业标准)

### 效率指标

| 指标 | 传统方式 | BOS-FS |
|------|---------|--------|
| 交付物完整性 | ~40% 项目缺失关键文件 | 100% 覆盖标准交付物 |
| 准备时间 | 1-2 周 | 半天 |
| 社区信任度 | 低 (缺乏标准文件) | 高 (对齐行业标准) |

## 场景 4: 安全服务交付

### 背景

安全工程师完成服务（渗透测试、代码审计、安全评估等）后，需要将技术发现转化为面向客户的交付文档。这是 BOS-FS 的核心应用场景之一。

### BOS-FS 如何帮助

| 阶段 | 传统方式 | BOS-FS 方式 |
|------|---------|------------|
| 原始数据整理 | 手动整理笔记、截图、Payload | 输入原始测试笔记，自动结构化 |
| 执行摘要编写 | 将技术语言翻译为商业语言 | 自动生成管理层可读的执行摘要 |
| 风险评估 | 手动计算 CVSS，编写影响分析 | 自动关联风险等级与业务影响 |
| 修复建议 | 凭经验编写 | 基于发现自动生成修复指南 |
| 报告排版 | Word/PPT 手动排版 | 结构化输出，一键生成多文档包 |

### 输入输出

**输入**: 原始测试笔记、漏洞发现、技术细节、截图、PoC 代码

**输出**:
- 执行摘要 (面向管理层)
- 技术发现详情 (面向技术团队)
- 风险评估矩阵
- 修复优先级列表
- 完整交付文档包

### 效率指标

| 指标 | 传统方式 | BOS-FS |
|------|---------|--------|
| 报告撰写时间 | 2-3 天 | 4-6 小时 |
| 技术→商业语言转换 | 手动，易遗漏 | 自动映射 |
| 报告一致性 | 依赖个人水平 | 标准化模板 |

### 典型子场景

- 渗透测试服务交付
- 代码审计服务交付
- 安全评估与差距分析
- 合规检查与整改建议
- 应急响应事件报告
- 漏洞台账管理

## 场景 6: 项目评审材料

### 背景

项目评审（立项评审、阶段评审、结项评审）需要准备大量标准化材料，准备过程耗时且容易遗漏关键信息。

### BOS-FS 如何帮助

| 阶段 | 传统方式 | BOS-FS 方式 |
|------|---------|------------|
| 材料准备 | 手动收集分散信息 | 自动聚合项目信息 |
| 评审视角模拟 | 无法预知评审关注点 | 模拟五类评审视角 |
| 风险识别 | 被动应对评审提问 | 提前识别潜在质疑点 |
| 通过率 | 不稳定 | 显著提升 |

### 输入输出

**输入**: 项目描述、进展报告、成果清单

**输出**:
- 项目概述
- 成果展示
- 风险与应对
- 评审问答预判
- 完整评审材料包

### 效率指标

| 指标 | 传统方式 | BOS-FS |
|------|---------|--------|
| 材料准备时间 | 1-2 天 | 2-4 小时 |
| 评审通过率 | ~50% | ~85% |
| 首次通过率 | ~30% | ~70% |

## 场景 7: 数据处理脚本交付

### 背景

数据/安全团队经常编写数据处理脚本（日志分析、数据清洗、格式转换），但缺乏文档，导致脚本无法跨项目复用，重复劳动严重。

### BOS-FS 如何帮助

| 阶段 | 传统方式 | BOS-FS 方式 |
|------|---------|------------|
| 脚本编写 | 写完即用，无文档 | 同时生成使用文档 |
| 使用说明 | 口头交接或简单注释 | 自动生成 README、使用指南 |
| 数据样例 | 无标准样例 | 自动生成测试数据样例 |
| 跨项目复用 | 需要重新理解脚本逻辑 | 文档完整，即拿即用 |
| 维护更新 | 脚本更新后文档过时 | 文档随脚本同步更新 |

### 输入输出

**输入**: 原始脚本、数据样例、处理逻辑描述

**输出**:
- README (项目说明、安装、使用)
- 使用指南 (详细步骤、参数说明)
- FAQ (常见问题解答)
- 示例数据与输出

### 价值

| 维度 | 说明 |
|------|------|
| 可复用性 | 脚本从"个人工具"变为"团队资产" |
| 知识沉淀 | 新人可直接使用，无需口头传授 |
| 质量保证 | 文档化过程暴露逻辑缺陷 |

## 场景 8: 团队知识沉淀

### 背景

团队的知识经验往往分散在个人头脑、聊天记录、临时文档中，缺乏结构化管理和传承机制，新人上手困难。

### BOS-FS 如何帮助

| 阶段 | 传统方式 | BOS-FS 方式 |
|------|---------|------------|
| 知识收集 | 分散在各处 | 统一结构化收集 |
| 知识整理 | 人工整理，耗时 | 自动分类、标准化 |
| 知识传承 | 师徒制，效率低 | 标准化文档，自助学习 |
| 新人培训 | 2-4 周 | 1-2 周 |

### 输入输出

**输入**: 项目经验、最佳实践、踩坑记录、流程文档

**输出**:
- 知识手册
- 最佳实践指南
- 常见问题解答
- 新人上手指南

### 价值

| 维度 | 说明 |
|------|------|
| 培训效率 | 新人上手时间缩短 50% |
| 知识一致性 | 减少对个人经验的依赖 |
| 可审计性 | 结构化知识便于审核和更新 |

## 决策指南

### 何时应该使用 BOS-FS

| 信号 | 说明 |
|------|------|
| 文档准备占项目时间 >20% | BOS-FS 可显著缩短文档周期 |
| 交付物质量参差不齐 | BOS-FS 提供标准化输出 |
| 评审通过率低 | BOS-FS 模拟评审，提前发现问题 |
| 新人上手慢，知识难传承 | BOS-FS 沉淀交付模板与流程 |
| 客户/评审对交付物反复提出修改 | BOS-FS 确保首次交付质量 |
| 多项目并行，交付压力大 | BOS-FS 提升并发处理能力 |

### 何时不适合

| 情况 | 说明 |
|------|------|
| 纯技术探索，无交付需求 | BOS-FS 关注交付而非生成 |
| 已有成熟自动化报告系统 | 需评估替代收益 |
| 项目周期极短 (<1天) | 引入成本可能超过收益 |

## 配置灵活性

BOS-FS 提供完整的配置系统，支持不同团队按自身标准定制：

- **自定义评审规则** — 调整维度权重、评分阈值、缺陷惩罚规则
- **自定义输出组件** — 增删交付物组件，选择输出格式（Markdown/JSON/HTML）
- **场景配置模板** — 预定义渗透测试/代码审计/漏洞台账等场景配置
- **配置加载优先级** — 硬编码默认值 < JSON 默认配置 < 用户自定义配置 < 场景配置
