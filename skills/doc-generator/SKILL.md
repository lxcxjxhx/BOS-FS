# Doc Generator
**version**: 0.1.0
> Context: [base_context](../knowledge/base_context.md)

## Role
基于真实交付案例与踩坑经验生成工程文档，解决"纯AI生成内容缺乏人感、过于抽象、无法保证正确性"的问题。

## Core Principles
| 原则 | 说明 |
|------|------|
| 真实场景优先 | 基于实际交付案例、踩坑记录、最佳实践，不使用"假设项目" |
| 人工校对保证 | 生成内容必须标注可信度（已验证/待验证/AI生成） |
| 可学习性 | 读者看完能理解主旨、能应用到实际项目 |
| 避免抽象示例 | 使用真实项目案例（可脱敏），禁用AI编造的示例代码 |

## Credibility Rating System
| 级别 | 标识 | 含义 | 可发布 |
|------|------|------|--------|
| ✅ 已验证 | `Verified` | 人工阅读过原文/原始资料，内容经过校对 | 是 |
| ⏳ 待验证 | `Pending` | AI辅助整理初稿，等待人工校对 | 仅限内部评审 |
| ⚠️ AI生成 | `AI-Generated` | 纯AI生成，未经验证，仅供参考 | 否，不可发布到知识库 |

## Document Generation Workflow

### Step 1: 收集真实素材
- 从 `real-world/` 目录、交付案例库、踩坑记录中收集素材
- 按主题归类：技术方案/踩坑经验/最佳实践/复盘总结
- 标注每个素材的来源路径

### Step 2: 生成初稿
- AI辅助整理文档结构，但**内容必须引用真实来源**
- 每个核心观点附带 `[来源: <路径或项目名称>]` 标注
- 初稿默认为 ⏳ 待验证 级别

### Step 3: 标注待验证项
- 明确标记哪些内容需要人工校对（技术细节/数据/结论）
- 使用 `<!-- TODO-VERIFY: <说明> -->` 标记

### Step 4: 人工校对
- 作者/领域专家确认内容正确性
- 核对技术细节与真实项目一致性

### Step 5: 更新可信度
- ⏳ 待验证 → ✅ 已验证（校对通过后）

### Step 6: 发布
- ✅ 已验证文档可发布至知识库
- ⚠️ AI生成文档禁止发布

## Quality Checklist
- [ ] 是否引用了真实案例或经验？（不能纯理论）
- [ ] 是否包含"踩坑经验"或"实战教训"章节？
- [ ] 是否标注了内容可信度级别？
- [ ] 读者能否从文中学习到可落地的知识？
- [ ] 是否避免了AI编造的示例代码？
- [ ] 核心观点是否有真实来源支撑？

## Output Schema

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "title": { "type": "string", "description": "文档标题" },
    "credibility": { "type": "string", "enum": ["Verified", "Pending", "AI-Generated"] },
    "sources": { "type": "array", "items": { "type": "string" }, "minItems": 1, "description": "真实来源路径列表" },
    "author": { "type": "string" },
    "reviewer": { "type": "string", "description": "人工校对者（Verified时必填）" },
    "tags": { "type": "array", "items": { "type": "string" } },
    "created_at": { "type": "string", "format": "date" }
  },
  "required": ["title", "credibility", "sources"],
  "additionalProperties": false
}
```

## Anti-Patterns
| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 纯AI生成无任何人校对 | 标注⚠️且不可发布到知识库 | 必须经过人工校对升级至✅ |
| 使用"假设项目"作为示例 | 读者无法落地 | 改用真实案例（可脱敏） |
| 缺少踩坑经验章节 | 文档像教科书，无实战价值 | 必须包含踩坑/教训章节 |
| 内容抽象无实际场景 | 读者学完无法应用 | 每个观点绑定真实场景 |
| 可信度标注缺失 | 读者无法判断内容可靠性 | 文档头部必须标注可信度 |

## Edge Cases
| 边界场景 | 处理方式 |
|----------|----------|
| 暂无真实案例可用 | 标注⚠️ AI生成，声明"暂无实战验证，仅供参考"，不可发布到知识库 |
| 专家无法及时校对 | 保持⏳ 待验证状态，限制仅在团队内部流转评审 |
| 敏感项目需要脱敏 | 脱敏规则：隐去客户名称/具体金额/内部架构细节，保留技术方案与教训 |
| 跨领域主题无对口专家 | 标注⚠️ AI生成，附带"建议寻找领域专家确认"提示 |

## Quality Gates
1. 文档头部是否包含可信度标注？
2. 是否至少引用1个真实来源？
3. 踩坑经验章节是否存在且内容具体？
4. 所有 `<!-- TODO-VERIFY -->` 标记是否已处理或明确标注？
5. 输出文档是否为合法 Markdown 且可正确渲染？
6. 是否避免了AI编造的代码示例？

## 方法论来源与学术诚信

本 Skill 的方法论来源于**真实工程交付经验与踩坑记录**，非 AI 凭空生成。

| 启发来源 | 核心贡献 |
|----------|----------|
| 真实项目交付案例 | 踩坑经验与最佳实践的来源 |
| 工程复盘文档 | 失败模式分析与教训总结 |
| 团队知识库 | 已验证的技术方案与设计决策 |

> **声明**: 本 Skill 旨在通过"AI辅助+人工校对"模式生成高质量工程文档。所有发布到知识库的内容必须经过人工验证。
